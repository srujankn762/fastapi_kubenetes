# FastAPI Customer CRUD API

This directory contains a FastAPI application that exposes CRUD endpoints for
customers and stores data in MySQL. FastAPI handles HTTP routing and OpenAPI
documentation; Pydantic validates API data; SQLAlchemy maps Python objects to
MySQL; Alembic versions schema changes; and MySQL persists data. Uvicorn runs
the application.

## 1. Project overview

The Customer resource has these fields:

| Field | Type | Rules |
| --- | --- | --- |
| id | integer | MySQL primary key, generated by the database |
| name | string | Required; 1–100 characters |
| age | integer | Required; zero or greater |
| gender | string | Required; 1–20 characters |

The application also exposes /, /health, and /db-health. The CRUD router is
mounted at /customers.

The components work together in this order:

1. FastAPI receives the request and selects the route.
2. Pydantic validates the JSON and produces a typed Python object.
3. SQLAlchemy turns the object into an INSERT, SELECT, UPDATE, or DELETE.
4. MySQL executes and persists the SQL.
5. FastAPI/Pydantic serializes the result to JSON and documents it in OpenAPI.

This resembles Django plus Django REST Framework (DRF), except FastAPI does
not bundle an ORM or migration system. SQLAlchemy and Alembic are selected
explicitly.

### Modules, packages, and __init__.py

A Python module is normally one importable .py file. A package is a directory
containing modules. An __init__.py file marks a directory as a traditional
Python package and may contain package-level initialization.

app, routers, and schemas contain __init__.py files so imports such as
from app.routers.customer import ... are unambiguous. The repository currently
contains app/models/__init__ without the .py extension. It is not the
conventional package initializer. Direct import of app.models.customer can
still work through modern namespace-package behavior, but
app/models/__init__.py would be the consistent layout. This README documents
that gap; it does not change it.

## 3. Application architecture

~~~text
Client
  -> FastAPI Router
  -> Pydantic Validation
  -> SQLAlchemy Session
  -> MySQL
  -> SQLAlchemy model/result
  -> Pydantic response serialization
  -> JSON response
~~~

The router is the HTTP layer: method, path, status code, body type, and
response model. Pydantic is the validation boundary, so invalid input normally
fails before database code runs. The SQLAlchemy session is the unit of work
used by each handler. MySQL provides persistence and database constraints.

There is no separate service or repository layer. Route functions perform
validation-to-model conversion and database work directly. That is reasonable
for this small project; a larger application could move business rules into
services without changing the public API.

## 4. Database connection

app/database.py contains:

~~~python
import os

from sqlalchemy import create_engine
from sqlalchemy.orm import declarative_base, sessionmaker

DATABASE_URL = os.environ["DATABASE_URL"]

engine = create_engine(
    DATABASE_URL,
    pool_pre_ping=True,
    pool_recycle=3600,
)

SessionLocal = sessionmaker(
    autocommit=False,
    autoflush=False,
    bind=engine,
)

Base = declarative_base()

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
~~~

DATABASE_URL is read from the environment. The app fails at import time if
it is absent. Compose builds it as:

~~~text
mysql+pymysql://${MYSQL_USER}:${MYSQL_PASSWORD}@mysql_database:3306/${MYSQL_DATABASE}
~~~

create_engine() creates SQLAlchemy's long-lived entry point and connection-pool
configuration. It does not mean one permanent connection is held for every
request. pool_pre_ping checks a pooled connection before use, while
pool_recycle=3600 recycles connections after about one hour to reduce stale
MySQL connection problems.

SessionLocal is a factory for short-lived ORM sessions. autocommit=False means
writes need an explicit commit(); autoflush=False prevents implicit flushes
before every operation. Base is the declarative base inherited by ORM models;
its metadata contains table definitions for SQLAlchemy and Alembic.

get_db() creates one session, yields it to the route, and closes it in finally,
including when the route raises an exception. Depends(get_db) tells FastAPI to
run this dependency and inject the yielded session:

~~~python
def list_customers(db: Session = Depends(get_db)):
    ...
~~~

An Engine is the application-wide SQLAlchemy entry point and pool. A Connection
is a lower-level checked-out database connection used for direct SQL; the
/db-health endpoint uses engine.connect() and executes SELECT 1. A Session is
the ORM unit of work: it tracks Customer objects, runs queries, stages
changes, and commits or rolls back transactions.

## 5. Customer model

app/models/customer.py defines:

~~~python
class Customer(Base):
    __tablename__ = "customers"

    id: Mapped[int] = mapped_column(
        primary_key=True,
        index=True,
    )
    name: Mapped[str] = mapped_column(
        String(100),
        nullable=False,
    )
    age: Mapped[int] = mapped_column(nullable=False)
    gender: Mapped[str] = mapped_column(
        String(20),
        nullable=False,
    )
~~~

Customer is an ORM class. __tablename__ maps instances to the MySQL table
named customers. Mapped[int] and Mapped[str] provide Python typing and
SQLAlchemy's typed mapping syntax. mapped_column() declares database columns
and constraints.

id is the primary key and has an index. name and gender use bounded string
columns. All four columns are non-null at the database level. The checked-in
migration creates the same columns, primary key, and ID index.

The Django equivalent is roughly:

~~~python
class Customer(models.Model):
    name = models.CharField(max_length=100)
    age = models.IntegerField()
    gender = models.CharField(max_length=20)
~~~

Django supplies an auto-incrementing primary key by default. SQLAlchemy makes
the mapped primary key explicit, so the table mapping is visible in the model.

## 6. Pydantic schemas

The actual schemas are:

~~~python
class CustomerCreate(BaseModel):
    name: str = Field(min_length=1, max_length=100)
    age: int = Field(ge=0)
    gender: str = Field(min_length=1, max_length=20)


class CustomerResponse(CustomerCreate):
    id: int

    model_config = ConfigDict(from_attributes=True)


class CustomerUpdate(BaseModel):
    name: str | None = Field(default=None, min_length=1, max_length=100)
    age: int | None = Field(default=None, ge=0)
    gender: str | None = Field(default=None, min_length=1, max_length=20)
~~~

BaseModel provides Pydantic parsing and validation. Field adds constraints.
CustomerCreate fields are required because they have no defaults. Update
fields are optional because PATCH must accept only fields that should change.

Update fields are typed as nullable, but the route explicitly rejects a
provided null with HTTP 422. This is different from an omitted field, which
means “leave the current value unchanged.”

model_dump() turns a validated Pydantic object into a dictionary. CREATE uses
payload.model_dump() as keyword arguments to Customer. UPDATE uses
payload.model_dump(exclude_unset=True), so omitted fields are not mistaken for
fields to update.

ConfigDict(from_attributes=True) lets CustomerResponse read attributes from a
SQLAlchemy object instead of requiring a dictionary. This is why GET routes can
return ORM objects directly.

Keeping ORM models and API schemas separate prevents database concerns from
automatically becoming the public contract. A table can gain an internal
column without exposing it, and input rules can differ from storage rules.
The closest DRF equivalent is a ModelSerializer, although these are explicit
Pydantic models rather than serializers generated from a Django model.

## 7. CRUD API implementation

The router is created with:

~~~python
router = APIRouter(prefix="/customers", tags=["Customers"])
~~~

It is included by app.main:app, so the final paths are /customers and
/customers/{customer_id}.

### CREATE — POST /customers

Request:

~~~http
POST /customers
Content-Type: application/json

{"name":"Anita Rao","age":29,"gender":"female"}
~~~

Response: HTTP 201 Created.

~~~json
{"id":1,"name":"Anita Rao","age":29,"gender":"female"}
~~~

Relevant implementation:

~~~python
@router.post("", status_code=status.HTTP_201_CREATED)
def create_customer(
    payload: CustomerCreate,
    db: Session = Depends(get_db),
):
    customer = Customer(**payload.model_dump())
    db.add(customer)
    db.commit()
    db.refresh(customer)
    return {
        "id": customer.id,
        "name": customer.name,
        "age": customer.age,
        "gender": customer.gender,
    }
~~~

Execution: FastAPI validates CustomerCreate; opens a session; model_dump()
becomes keyword arguments for a new ORM object; db.add() stages it;
db.commit() executes the INSERT; db.refresh() reloads the generated ID; and
the explicit dictionary is returned with HTTP 201. FastAPI then closes the
session through get_db(). This route has no response_model; it builds the
response dictionary explicitly. In DRF, this is commonly a serializer
create() method called by CreateAPIView or ModelViewSet.

### READ ALL — GET /customers

Request:

~~~http
GET /customers
~~~

Response: HTTP 200 OK.

~~~json
[
  {"id":1,"name":"Anita Rao","age":29,"gender":"female"}
]
~~~

~~~python
@router.get("", response_model=list[CustomerResponse])
def list_customers(db: Session = Depends(get_db)):
    statement = select(Customer)
    customers = db.scalars(statement).all()
    return customers
~~~

select(Customer) builds a SELECT statement for the ORM entity. db.scalars()
extracts Customer objects rather than row tuples, and .all() materializes the
list. CustomerResponse serializes each ORM object using from_attributes=True.
There is currently no pagination or filtering. DRF's usual equivalent is a
ListAPIView or viewset list action.

### READ ONE — GET /customers/{customer_id}

Request:

~~~http
GET /customers/1
~~~

Response: HTTP 200 OK.

~~~json
{"id":1,"name":"Anita Rao","age":29,"gender":"female"}
~~~

~~~python
@router.get("/{customer_id}", response_model=CustomerResponse)
def get_customer(
    customer_id: int,
    db: Session = Depends(get_db),
):
    customer = db.get(Customer, customer_id)
    if customer is None:
        raise HTTPException(
            status_code=404,
            detail="Customer not found",
        )
    return customer
~~~

FastAPI converts the path segment to an integer. db.get(Customer, customer_id)
performs a primary-key lookup. A missing row returns HTTP 404; otherwise the
ORM object is serialized as CustomerResponse. This resembles DRF's
get_object_or_404() pattern.

### UPDATE — PATCH /customers/{customer_id}

Request:

~~~http
PATCH /customers/1
Content-Type: application/json

{"age":30}
~~~

Response: HTTP 200 OK.

~~~json
{"id":1,"name":"Anita Rao","age":30,"gender":"female"}
~~~

Core implementation:

~~~python
customer = db.get(Customer, customer_id)
if customer is None:
    raise HTTPException(status_code=404, detail="Customer not found")

update_data = payload.model_dump(exclude_unset=True)
for field, value in update_data.items():
    if value is None:
        raise HTTPException(
            status_code=422,
            detail=f"{field} cannot be null",
        )
    setattr(customer, field, value)

db.commit()
db.refresh(customer)
return customer
~~~

Pydantic validates each supplied field, then the route looks up the row.
exclude_unset=True makes {"age": 30} become only {"age": 30}; name and
gender remain unchanged. setattr() changes each supplied ORM attribute.
commit() persists the UPDATE and refresh() returns current database values.

Missing customers return 404. Invalid types and constraints return 422 from
Pydantic. An explicitly supplied null reaches the route and returns 422
because the database columns are non-nullable. PATCH is a partial update;
PUT conventionally replaces the complete resource. This project implements
PATCH only, not PUT. In DRF, this resembles a serializer with partial=True
followed by save().

### DELETE — DELETE /customers/{customer_id}

Request:

~~~http
DELETE /customers/1
~~~

Response: HTTP 204 No Content with an empty body.

~~~python
@router.delete(
    "/{customer_id}",
    status_code=status.HTTP_204_NO_CONTENT,
)
def delete_customer(
    customer_id: int,
    db: Session = Depends(get_db),
):
    customer = db.get(Customer, customer_id)
    if customer is None:
        raise HTTPException(
            status_code=404,
            detail="Customer not found",
        )
    db.delete(customer)
    db.commit()
~~~

The route finds the row by primary key, returns 404 if absent, marks the ORM
object for deletion, and commits the DELETE. This is a hard delete: the row is
removed permanently. There is no deleted_at column or soft-delete filter.
DRF's DestroyAPIView or a viewset destroy action is similar.

## 8. Alembic migrations

Alembic is SQLAlchemy's schema migration tool. A migration records a deliberate
database structure change so another environment can reproduce it. The
existing revision 89864a2e3933_create_customers_table.py creates customers and
its ID index; downgrade() drops them.

* alembic.ini sets script_location = /app/alembic, logging, and a placeholder
  sqlalchemy.url.
* alembic/env.py imports DATABASE_URL and calls
  config.set_main_option("sqlalchemy.url", DATABASE_URL).
* Base.metadata is where SQLAlchemy knows about mapped tables. env.py imports
  Customer so it is registered before metadata is inspected.
* upgrade() applies a revision; downgrade() reverses it.
* Alembic stores the current revision ID in the alembic_version table.

Typical commands are:

~~~bash
alembic revision --autogenerate -m "describe the schema change"
alembic upgrade head
alembic current
~~~

Review autogenerated migrations before applying them. Autogenerate compares
known SQLAlchemy metadata with the database, but cannot safely infer every
rename, data migration, semantic change, or business rule.

### Current configuration caveats

env.py first assigns target_metadata = Base.metadata, but later the template
line target_metadata = None assigns None again. Autogenerate therefore cannot
use model metadata as intended. The checked-in migration is still an explicit
revision and can be applied. Fixing this is an application change and is
outside this README task.

The Dockerfile copies requirements.txt and app, but not alembic/ or
alembic.ini. Compose's bind mount ./fastapi-hello-world:/app makes them
available in the Compose container. A standalone image made only from the
Dockerfile therefore does not contain migration files unless supplied
separately.

MySQL DDL has transactional limitations. Some schema operations can implicitly
commit or cannot roll back like ordinary data changes. Test migrations against
a safe database and review locking and compatibility implications.

In Django, makemigrations creates migration files and migrate applies them.
Alembic provides the same broad workflow, but configuration and revision
scripts are more explicit and separate from FastAPI.

## 9. Docker and local development

The Dockerfile uses python:3.12-slim, sets unbuffered Python output, installs
requirements.txt, copies app to /app/app, exposes port 8000, and starts:

~~~bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
~~~

docker-compose.yaml defines:

* fastapi_backend: built from ./fastapi-hello-world, maps host 8000 to
  container 8000, and bind-mounts the project at /app. Its overridden command
  enables --reload.
* mysql_database: runs mysql:8.4, maps host 3308 to container 3306, and
  persists data in the named volume mysql_data.

Inside the Compose network the API uses mysql_database:3306. Host tools such
as DBeaver use localhost:3308. Container-to-container traffic does not use
localhost or the host mapping.

Compose substitutes MYSQL_ROOT_PASSWORD, MYSQL_DATABASE, MYSQL_USER, and
MYSQL_PASSWORD. They initialize MySQL and construct the API's
mysql+pymysql://...@mysql_database:3306/... URL. Keep real values in a local
.env file or approved secret store; never commit passwords or tokens. This
repository has no .env file. GitHub Codespaces can provide the values through
Codespaces secrets or environment configuration.

From the repository root:

~~~bash
docker compose up --build
./run.sh
docker compose down
docker compose logs -f fastapi_backend
docker compose logs -f mysql_database
docker compose ps
~~~

From fastapi-hello-world/, direct local development is:

~~~bash
pip install -r requirements.txt
export DATABASE_URL='mysql+pymysql://USER:PASSWORD@HOST:3306/DATABASE'
uvicorn app.main:app --reload
~~~

This requires a reachable MySQL instance. The standalone Docker commands from
the original README are valid when the URL is supplied:

~~~bash
docker build -t fastapi-hello-world .
docker run --rm -p 8000:8000 \
  -e DATABASE_URL='mysql+pymysql://USER:PASSWORD@HOST:3306/DATABASE' \
  fastapi-hello-world
~~~

## 10. API testing

Open http://localhost:8000/docs for FastAPI's interactive Swagger UI. It is
generated from routes and Pydantic models. The OpenAPI document is at
http://localhost:8000/openapi.json.

End-to-end curl sequence:

~~~bash
curl http://localhost:8000/
curl http://localhost:8000/health
curl http://localhost:8000/db-health

curl -i -X POST http://localhost:8000/customers \
  -H 'Content-Type: application/json' \
  -d '{"name":"Anita Rao","age":29,"gender":"female"}'

curl -i http://localhost:8000/customers
curl -i http://localhost:8000/customers/1

curl -i -X PATCH http://localhost:8000/customers/1 \
  -H 'Content-Type: application/json' \
  -d '{"age":30}'

curl -i -X DELETE http://localhost:8000/customers/1
curl -i http://localhost:8000/customers/1
~~~

The last request should return 404. In DBeaver, while Compose is running, use
MySQL host localhost, port 3308, the database from MYSQL_DATABASE, and the
configured non-root user/password. If DBeaver runs in another container, use
the Compose network and mysql_database instead. Query customers to verify the
API calls.

## 11. Django vs FastAPI quick reference

| Concern | This FastAPI project | Django/DRF equivalent |
| --- | --- | --- |
| URL routing | APIRouter, decorators, include_router() | urls.py patterns |
| Views | Route functions such as create_customer() | Django views, generic views, or viewsets |
| Serializers | Pydantic BaseModel schemas | DRF serializers / ModelSerializer |
| ORM models | SQLAlchemy Base and Customer | Django models.Model |
| Queries | select(), db.scalars(), db.get() | QuerySets such as objects.all() |
| Sessions/transactions | Explicit SQLAlchemy Session and commit() | Django connection management and transaction.atomic() |
| Migrations | Alembic revisions and upgrade head | makemigrations and migrate |
| Validation | Pydantic annotations and Field | DRF serializer validation |
| Dependency injection | FastAPI Depends(get_db) | No direct built-in equivalent |
| API documentation | FastAPI-generated OpenAPI/Swagger | DRF schema tooling or an OpenAPI package |

## 12. Common errors and troubleshooting

### ModuleNotFoundError for routers or schemas

Cause: Uvicorn was started from the wrong directory, the import path is wrong,
or Python cannot see app. Run from fastapi-hello-world/ with
uvicorn app.main:app --reload; confirm the files exist. In Compose, confirm
the bind mount is /app.

### Missing or unusual __init__.py

Cause: a package initializer is missing; this repository has
app/models/__init__ without .py. Inspect exact filenames. Direct imports may
work through namespace-package behavior, but app/models/__init__.py is the
conventional fix if tooling has trouble.

### MySQL authentication requires cryptography

Some MySQL authentication plugins require cryptography when PyMySQL connects.
This project includes cryptography>=44,<47. Rebuild after dependency changes
and verify the container installed requirements. Do not weaken authentication
blindly.

### Incorrect DATABASE_URL

Cause: missing driver, wrong host/port, or wrong database/user. The driver here
is mysql+pymysql. Verify the variable without exposing the password, call
/db-health, inspect logs, and match the execution context. Compose uses
mysql_database:3306, not localhost:3308.

### Missing Alembic configuration

Cause: Alembic cannot find alembic.ini, its script directory, or the
environment URL. Run from fastapi-hello-world/ locally, or from /app inside
Compose. The current alembic.ini uses /app/alembic, so a host-only invocation
may not work as written.

### Missing target_metadata

Cause: env.py assigns Base.metadata and later overwrites it with None.
Inspect env.py; an empty or incomplete autogenerated migration is a warning
to fix the metadata setup before applying it.

### MySQL connection refused

Cause: MySQL is stopped, still initializing, or the wrong address is used.
Run docker compose ps and docker compose logs mysql_database. From the API
container use mysql_database:3306. depends_on starts MySQL first but does not
guarantee it is ready to accept connections.

### Docker port mapping confusion

The mappings are 8000:8000 for FastAPI and 3308:3306 for MySQL. Use
localhost:8000 for curl/browser, localhost:3308 for a host database client,
and mysql_database:3306 from the API container.

### Database table not found

Cause: the customers migration was not applied, or the API uses a different
database. Check DATABASE_URL, inspect DBeaver, then run:

~~~bash
alembic upgrade head
alembic current
~~~

The named MySQL volume preserves data across normal container recreation, so
changing initialization variables does not recreate an existing schema.

## 13. Key takeaways

* FastAPI routes define the HTTP contract; Pydantic schemas define the API
  data contract; SQLAlchemy models define persistence mapping.
* Depends(get_db) supplies one session per request and guarantees cleanup.
* commit() persists changes; refresh() reloads generated/current values.
* exclude_unset=True is what makes PATCH partial.
* from_attributes=True allows response schemas to serialize ORM objects.
* Compose uses mysql_database:3306 internally and localhost:3308 from the host.
* Alembic revisions are schema history and must be reviewed before execution.
* There is currently no pagination, filtering, auth, soft delete, service
  layer, or PUT endpoint.
* Before relying on Alembic autogenerate, address the target_metadata = None
  overwrite in alembic/env.py.
